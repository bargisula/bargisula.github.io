# /ai-dev-workflow：AI 協作開發系統

**用法：**

```
/ai-dev-workflow prd [產品想法]     → 建立 PRD（產品需求文件）
/ai-dev-workflow sdd               → 從 PRD 產出 SDD（系統設計文件）
/ai-dev-workflow spec              → 從 SDD 產出 Spec（執行規格）
/ai-dev-workflow tasks             → 從 Spec 拆解 Task Inventory
/ai-dev-workflow run [Task 編號]   → 執行指定 Task
/ai-dev-workflow verify [Task 編號]→ 驗收指定 Task 的完成回報
```

**核心理念：** 人的判斷往前移——PRD/SDD/Spec 全部定義清楚，後面讓 AI 在規則裡互相接力執行與驗收，不需要每一步都回來問人。

---

## 檔案結構

所有工作文件存於：

```
data/dev/{專案名稱}/
├── prd.md
├── sdd.md
├── spec.md
└── tasks.md         ← Task Inventory
```

---

## Phase 1：PRD

**觸發：** `/ai-dev-workflow prd [想法]`

**你的角色：** 產品架構師。這一輪只做產品判斷，不進工程方案，不寫 code。

請依序與使用者確認以下 10 個問題（可批量回覆，不需逐一問）：

1. 這個功能要解決的核心問題是什麼？
2. 主要使用者是誰？在什麼情境下使用？
3. 現在的痛點是什麼？為什麼現在的方式不夠好？
4. MVP 做到哪裡就好？最精簡的有效版本是什麼？
5. 哪些功能現在不做？
6. 哪些想法應該放 Roadmap？
7. 有哪些產品風險（技術、用戶採用、商業）？
8. 什麼指標或體驗改善代表成功？
9. 有沒有競品或參考對象？
10. 什麼狀態才算產品完成？

確認後產出 `data/dev/{專案名稱}/prd.md`，格式：

```markdown
# PRD：{產品/功能名稱}

## 核心問題
{這個功能為什麼存在，解決什麼根本痛點}

## 使用者與情境
- **對象：** {誰}
- **情境：** {什麼時候、什麼狀況下會用}

## MVP 範圍
{做到哪裡就算完成，不需要更多}

## 明確排除（Non-scope）
- {現在不做的功能 1}
- {現在不做的功能 2}

## Roadmap（未來才做）
- {未來功能 1}

## 成功標準
{什麼狀態代表這個功能成功}

## 產品風險
- {風險 1：說明為什麼風險 + 如何觀察}

## 完成定義
{具體、可驗證的完成條件}
```

存檔後輸出：
```
PRD 完成。若已對齊產品方向，輸入 /ai-dev-workflow sdd 進入系統設計。
```

## Phase 2：SDD

**觸發：** `/ai-dev-workflow sdd`

**前置：** 必須先有 `data/dev/{專案名稱}/prd.md`。若找不到，提示先跑 `/ai-dev-workflow prd`。

**你的角色：** 系統架構師。這一輪只做系統設計，不實作，不寫 code。

讀取 PRD，產出 `data/dev/{專案名稱}/sdd.md`，格式：

```markdown
# SDD：{產品/功能名稱}

## 模組定位
{這個功能屬於哪個模組，與現有模組的關係}

## 資料流
{資料從哪裡來，怎麼流動，怎麼儲存}

| 資料來源 | 同步方式 | 目的地 | 頻率 |
|---|---|---|---|
| {來源} | {方式} | {目的地} | {頻率} |

## 前端影響
- 頁面：{哪些頁面受影響}
- 新增/修改的 component：{清單}
- 狀態管理：{哪些 state 需要新增或調整}

## 後端 / API 影響
- 新增 API：{清單}
- 修改 API：{清單}
- 刪除 API：{清單}

## 資料庫 / Schema 影響
- 新增欄位：{清單}
- 新增資料表：{清單}
- 是否需要 migration：{是/否，說明}

## 權限與角色
{誰能做什麼，怎麼切}

## 可共用模組
{可以重用的 component / service / util}

## 高風險區域
- {風險點 1：為什麼高風險}
- {風險點 2}

## 不要過早設計的地方
{現在故意留白的決策，以及理由}

## 需保留擴充彈性的地方
{未來可能要改的地方，現在怎麼設計才不會阻礙}
```

存檔後輸出：
```
SDD 完成。輸入 /ai-dev-workflow spec 進入執行規格。
```

## Phase 3：Spec

**觸發：** `/ai-dev-workflow spec`

**前置：** 必須先有 SDD。若找不到，提示先跑 `/ai-dev-workflow sdd`。

**你的角色：** 技術規格師。產出可以直接交給 AI 執行的施工圖。

讀取 PRD + SDD，產出 `data/dev/{專案名稱}/spec.md`，格式：

```markdown
# Spec：{產品/功能名稱}

## 本輪目標
{一句話說明這個 Spec 要完成什麼}

## Scope（本輪做什麼）
- {具體要實作的項目 1}
- {具體要實作的項目 2}

## Non-scope（本輪不做什麼）
- 不改 schema
- 不做 migration（除非 Scope 明確包含）
- 不重構既有模組
- 不碰正式資料或 production 設定
- 不把 Roadmap 功能提前實作
- {專案特有的限制}

## 可修改的範圍
- 檔案：{可以動的檔案或目錄清單}
- 模組：{可以改的模組}

## 不可修改的範圍
- 檔案：{禁止動的檔案}
- 模組：{禁止動的模組}
- 資料：{禁止碰的資料或環境}

## 操作權限分級

### 可自動執行（不需確認）
- 讀取檔案、搜尋程式碼
- 查看 git status / log
- 執行型別檢查、跑測試
- 整理修改計畫、產出回報

### 可執行但需回報
- 提出技術方案
- 比較實作方式
- 補充測試計畫

### 必須停下來確認
- 修改 schema 或 migration
- 刪除或批次修改資料
- 改動 production 設定
- 大範圍重構
- 超出本輪 Spec 的任何行為

## API 行為規格
{若有 API 變更，明確列出 endpoint、request/response 格式、錯誤處理}

## UI 狀態規格
{若有前端，明確列出各狀態：空值、載入中、錯誤、成功}

## 驗收標準
- {具體、可執行的驗收條件 1}
- {具體、可執行的驗收條件 2}

## 驗證命令
```bash
{跑完後要執行什麼命令來驗證}
```

## 是否允許 commit：{是/否}
## 是否允許 push：{是/否，說明條件}
```

存檔後輸出：
```
Spec 完成。輸入 /ai-dev-workflow tasks 拆解任務清單。
```

## Phase 4：Task Inventory

**觸發：** `/ai-dev-workflow tasks`

**前置：** 必須先有 Spec。

**拆解原則（Atomic Task 標準）：**

- 每個 Task 只有單一目的
- 每個 Task 可以在單輪內完成
- 每個 Task 可以由另一個 AI 驗收
- 不把多個模組塞進同一個 Task
- 高風險 Task 標記 `⚠️ 需人工確認`

讀取 Spec，產出 `data/dev/{專案名稱}/tasks.md`，格式：

```markdown
# Task Inventory：{專案名稱}

**來源 Spec：** data/dev/{專案名稱}/spec.md
**總 Task 數：** {N}
**最後更新：** {日期}

---

## Task 清單

| # | 名稱 | 狀態 | 風險 |
|---|---|---|---|
| T001 | {名稱} | ⬜ 待執行 | — |
| T002 | {名稱} | ⬜ 待執行 | ⚠️ 需人工確認 |

---

## Task 詳細

### T001：{任務名稱}

**目標：** {一句話說明這個 Task 要做什麼}

**Scope：**
- {具體要改的東西}

**Non-scope：**
- {這個 Task 明確不做的事}

**可能影響的檔案：**
- `{路徑}`

**不可碰的範圍：**
- `{路徑或模組}`

**驗收方式：**
- {可以客觀驗證的條件}

**驗證命令：**
```bash
{具體命令}
```

**完成回報格式：**
見固定回報格式（下方）

**下一步銜接：** T002

---
```

存檔後輸出：
```
Task Inventory 完成，共 {N} 個 Task。
輸入 /ai-dev-workflow run T001 開始執行第一個 Task。
```

## Phase 5：執行 Task

**觸發：** `/ai-dev-workflow run [Task 編號]`

讀取 `data/dev/{專案名稱}/tasks.md` 確認指定 Task 的完整規格，然後執行。

**執行前確認清單（強制）：**

1. 確認當前 branch 與最新 commit
2. 確認任務狀態為「待執行」
3. 確認本 Task 的 Scope 和 Non-scope
4. 確認不碰的高風險範圍

**執行限制（每次都適用）：**

- 只處理指定 Task，不順手做下一個
- 不擴大 Scope
- 不修改 Non-scope 內的任何東西
- 碰到高風險操作必須停下來等確認
- 發現 Spec 有歧義，回報而非自行決定

**完成後，強制輸出固定回報格式：**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✅ Task 完成回報
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Task 編號：{T001}
Task 名稱：{名稱}
執行時間：{日期}

commit hash：{hash}
commit message：{message}
是否已 push：{是 / 否，branch 名稱}

修改檔案：
  - {路徑}：{說明改了什麼}

修改內容摘要：
{2-3句說明做了什麼，不是列步驟，是說結果}

本機驗證命令：
  {命令}

驗證結果：
  {PASS / FAIL，若 FAIL 說明原因}

尚未完成：
  {若有遺留，說明；若無，填「無」}

是否超出 Scope：
  {是（說明） / 否}

是否碰到 Non-scope：
  {是（說明） / 否}

需人工確認的風險：
  {若有，說明；若無，填「無」}

下一個建議 Task：T{下一個編號}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

回報完成後，更新 `tasks.md` 中該 Task 的狀態：
- PASS → `✅ 已完成`
- FAIL → `❌ 需重做`

---

## Phase 6：驗收 Task

**觸發：** `/ai-dev-workflow verify [Task 編號]`

**你的角色：** 只做驗收，不直接修改任何東西。

讀取：
1. `tasks.md` 中該 Task 的 Spec
2. 上一輪的完成回報（從對話取得）

**驗收檢查清單：**

| 項目 | 判定 |
|---|---|
| 是否只處理指定 Task | ✅ / ❌ |
| 是否有超出 Scope | ✅ / ❌ |
| 是否碰到 Non-scope | ✅ / ❌ |
| 修改內容是否符合 Spec | ✅ / ❌ |
| 驗證命令是否足夠 | ✅ / ❌ |
| 驗證結果是否可信 | ✅ / ❌ |
| 是否需要補測 | 是 / 否 |

**輸出驗收結論：**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔍 驗收結論：T{編號}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
結論：通過 / 不通過 / 需補件

理由：
{具體說明，若不通過必須有可操作的修改方向}

需要補的地方：
{若有，具體說明；若無，填「無」}

下一個 Task：T{編號}

─── 可直接貼給執行端的下一輪指令 ───
T{上一個} 驗收通過。請開始 T{下一個}。
請只處理 T{下一個}，不處理後續 Task，不擴大 Scope。
完成後依固定格式回報。
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 快速查詢：哪裡最容易失敗

| 風險 | 說明 | 預防方式 |
|---|---|---|
| PRD 不清楚 | 後面所有工作都方向錯 | 在 Phase 1 多花時間，對清楚再往後 |
| Task 太大 | AI 開始自作主張 | 每個 Task 要能單輪完成、單輪驗收 |
| Non-scope 沒寫 | AI 熱心過頭，順手多做 | 每個 Task 和 Spec 都要明確列 Non-scope |
| 回報格式不固定 | 下一輪 AI 要重新理解 | 每次都用固定回報格式，不簡化 |
| 人完全不看 | 方向跑歪沒人抓 | 產品方向、風險紅線、正式環境仍由人確認 |

---

## 設計原則

- **人的判斷往前移：** 把產品決策、系統邊界、風險紅線全部定在 Phase 1-3，後面才能讓 AI 跑
- **Non-scope 比 Scope 更重要：** AI 不會做太少，會做太多，Non-scope 是護欄
- **完成回報是交接介面：** 格式固定才能讓下一個 AI 直接讀，不用重新解釋
- **驗收要求證據，不是相信「完成了」：** commit hash、修改檔案、驗證結果都要有
- **Task 要小到可以單輪驗收：** 太大就拆，不要讓 Task 包含隱含決策
